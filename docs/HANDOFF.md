## 4. 원본과 비교하는 방법 (검증 규칙)

- 원본 탭과 우리 탭 모두 **뷰포트 1280×900**으로 맞춘다 (`resize_window`). **탭을 바꾸면 에뮬레이션이 풀리므로** 매번 다시 맞춘다.
- 같은 문구를 가진 요소의 `getBoundingClientRect()` 위치·크기·글자 크기를 양쪽에서 읽어 비교한다. 오차 1px 이내를 목표로 한다. (원본 DOM 덤프용 `dump(root)` 헬퍼를 콘솔에서 즉석으로 만들어 썼다.)
- **스크롤 동작은 코드로 `scrollTo` 점프하지 말고 실제 휠 스크롤로** 테스트한다 (`computer` 도구의 `scroll`, 1칸 = 100px, 한 번에 최대 10칸). 점프하면 헤더 상태가 달라져서 착시가 생긴다 (이번에 한 번 속았다).
- `loading="lazy"` 이미지는 화면 근처에 와야 불러온다. 배포 확인 때 "안 불러졌다"는 오판이 쉽다. 보이는 위치까지 스크롤해서 확인한다.
- 원본 내용은 시간이 지나면 바뀐다 (리뷰 날짜, 인기 검색어, 일부 이미지 높이로 인한 y 위치 등). 위치 비교는 "섹션 내부 상대 좌표"로 한다.
- 정적인 기준 좌표(원본, 1280×900, 스크롤 0): 헤더 상단 줄 50~131, 카테고리 줄 131~183, 히어로 261, 탭 바 1400(높이 54), 본문 시작 1534, 스타일링샷 640px, "함께 둘러보면 좋아요" 2254(451px), 상품정보 2785.

## 6. 남은 문제 (우선순위 순) — 2026-10 실제 휠 스크롤 비교 결과

### 6-1. 스크롤 시 헤더 동작이 반대다 (가장 큰 문제)

원본은 **스크롤을 내려도 헤더 상단 줄이 사라지지 않는다.**

| 스크롤 위치(휠) | 원본 | 우리(현재) |
| --- | --- | --- |
| 0 | 정적 헤더(배너 50 + 상단 줄 81 + 카테고리 줄 52). 고정 요소 없음. 탭 바 sticky top 132, 카드 186(높이 714) | 정적 헤더. 고정 헤더는 화면 밖(-133)에 숨김 |
| 100px 내림 | 상단 줄(로고·GNB·검색·로그인·글쓰기, 81px)이 `position: fixed; top: 0; z-index: 1102`로 나타남. 탭 바 sticky top 80, 카드 134 | 아무것도 안 나타남 |
| 200px 이상 내림 | 상단 줄 유지 + 카테고리 줄이 그 **뒤**(top 29, z 1101)에 겹쳐 숨음. 탭 바 80, 카드 134(높이 766) | 고정 헤더가 숨은 채. 탭 바 위에 80px 빈 띠가 생김 |
| 위로 1칸 올림 | 카테고리 줄이 슬라이드로 내려옴(top 81). 탭 바 sticky top **132**, 카드 **186**(높이 **714**) | 탭 바 133, 카드 187(713)로 거의 같음 |

고칠 방향: 현재 `useHeaderVisible`(SiteHeader.tsx)은 "내리면 숨김/올리면 표시"로 되어 있다. 원본처럼 **내릴 때는 상단 줄만 고정(탭 바 top 80, 카드 134), 올릴 때는 두 줄 모두(탭 바 132, 카드 186)** 로 바꾼다. 카드 높이는 `calc(100vh - top)` 이므로 그대로 두면 된다. 헤더 높이 상수는 `StickyTabs.tsx`의 `TAB_TOP_*`.

### 6-2. 탭 이동·강조 기준이 다르다

- 탭 클릭 시: 원본은 이동한 영역 제목이 화면 위 **154px**(고정 탭 바 아래 20px 여백)에 온다. 우리는 134px. (`StickyTabs.tsx`의 `go`: 마지막에 `- 20` 추가)
- 탭 강조: 원본은 영역이 화면 위 **약 225px**(= 화면 높이의 25%)까지 올라오면 해당 탭이 강조된다. 우리는 154px. (`useActiveSection`의 `offset`을 `window.innerHeight * 0.25`로)

### 6-4. 그 밖의 알려진 한계 (우선순위 낮음)

- 맨 아래 추천 목록은 16개로 두기로 했다(사용자 결정). 원본은 사람마다 다른 추천이 끝없이 이어져서(문서 높이 98,000px 이상, 화면 줄만 렌더링) 같은 목록을 옮길 수 없다.
- 리뷰/문의는 1~9쪽이 모두 바뀐다(데이터: `data/reviewPages.ts`, `data/qnaPages.ts`). 원본 API는 CORS로 막혀 있어 정적 데이터이고 시간이 지나면 원본과 달라진다. 리뷰의 베스트순/최신순, 별점·옵션(여러 개 선택) 필터는 옮겨 둔 45개 안에서만 동작한다(원본은 15,000개 이상 전체). 옵션 목록도 이 45개에 나온 옵션 11개뿐이다.
- 리뷰 "도움돼요" 엄지 아이콘은 원본 Lottie의 정지 프레임(윤곽)과 눌렀을 때 채워진 모양을 옮겼다. 원본의 눌렀을 때 퍼지는 선 애니메이션은 없다.
- 이미지는 오늘의집 이미지 서버와 `marketb.kr`을 **직접 참조**한다. 그쪽이 막거나 바꾸면 깨질 수 있지만, 저장소로 가져오지 않기로 했다(사용자 결정).
- 상세 이미지 9장(오늘의집 2장 + marketb 7장)은 배포 환경에서 모두 불러와지는 것을 확인했다. 기다리는 시간이 짧으면 안 불러온 것처럼 보이니 이미지당 5초 이상 기다려 확인한다.

## 7. 3D "내 공간에 맞는지 확인하기" 팝업 (유지해야 하는 기존 기능)

진입: 대표 이미지 오른쪽 아래 "내 방에 맞을까? 가상배치" 버튼 → `FitModal`(`React.lazy`, z-index 2000). 색상은 구매 패널에서 마지막으로 고른 색을 따른다.

- **방**: 기본 `6000×6000mm`, 천장 2600, 문 900. 프리셋은 "넓은 침실 · 책상 아래" 하나. 기본 가구 배치는 `catalog.ts`의 `wideFurniture`(침대·책장·소파·화분·책상·의자 + 러그 2개). 방이 `3800×3600`보다 작으면 옛 3종 배치(`isWideRoom` in `room.ts`).
- **시점**: 아이소메트릭에 가까운 좁은 화각(fov 24°), 앞쪽 벽(-x, +z)은 카메라가 바깥에 있으면 거의 투명. 마루판 바닥 / 흰 타일 벽 / 창(초록 풍경+블라인드) / 벽 조명·선반.
- **3D 영역 도구**: 오른쪽 위 확장/축소 버튼(누르면 오른쪽 패널 숨김), 하단 툴바 `90° 회전 · 벽에 붙이기 · 서랍 열어보기 · 위에서 보기 · 초기화`, 하단 안내 "실측 규격 W×D×H | 서랍 앞 여유".
- **오른쪽 패널**: 탭(방 화면: `내 공간 치수 / 함께 둔 가구 / 색상`, 상세 화면: `내 책상 치수 / 서랍장 위치·바퀴 / 색상`) + 항상 보이는 "공간 적합도 진단"(주변 간격은 아코디언).
- **상세 뷰**(책상 클릭 또는 "책상·서랍장 치수 자세히 입력하기"): 책상 기준 좌표 360° 뷰, 치수선(mm), 서랍장 위치(왼쪽/오른쪽 다리 쪽, 다리·뒤 간격) 입력, **바퀴 on/off + 바퀴 높이(20~100mm, 기본 30)**. 제품 높이 = 본체 655 + 바퀴.
- **모달 문구**: 제목 "내 공간에 맞는지 확인하기", 설명 문장 없이 안내만 둔다( 방 전체 보기 "방을 둘러보고, 가구를 배치해 보세요." / 책상·서랍장 상세 보기 "책상 치수와 서랍장 위치를 조정하고, 설치 조건을 확인해 보세요."). 진입 버튼 왼쪽에는 캐릭터(`WavingCharacter.tsx`, 136px)가 버튼 밖에 따로 있고, 버튼에 가까운 오른손이 버튼 글자와 같은 높이가 되도록 버튼을 바닥에서 30px 띄웠다(캐릭터 크기를 바꾸면 이 값도 다시 맞춘다). 눌러도 아무 일도 없고(장식), 두 팔(NEW 팻말을 든 왼팔·가리키는 오른팔)을 번갈아 흔들며 계속 뛴다. 한 장짜리 이미지(`src/assets/oh-character-new.webp`)를 팔 부분만 잘라 겹치고 어깨를 축으로 회전시킨 것이며(애니메이션은 `index.css`의 `oh-hop`·`oh-wave-*`), 팔이 빠진 몸통 자리는 파란 조각으로 메운다. 팻말에 가려 있던 머리 왼쪽 모서리는 둥근 곡선으로 그려 넣었다. 움직임 줄이기 설정에서는 멈춘다. 상세 뷰 "내 책상 치수" 탭은 설치 공간 치수(상판 아래 높이·다리 안쪽 폭) + 접을 수 있는 책상 전체 크기 + 치수 입력 안내 구성이다. 페이지(탭) 제목은 ROOMJIRAK.
- **제품 규격**: 가로 280 × 세로 410 × 높이 685mm(바퀴 30mm 포함, 본체 655). 헤더 문구 옆에 "① 책상 치수 입력 → ② 서랍장 위치 조정 → ③ 설치 조건 확인" 안내가 있다. 판정 결과 제목은 "입력한 치수 기준으로 배치 가능해요" / "현재 배치에서는 사용 공간이 부족해요".
- **판정 기준**(`lib/fit.ts` `evaluate`): 방 밖/천장 초과 불가, 겹침 불가(단 책상 아래 높이 ≥ 제품 높이면 "아래에 들어감"), 책상 다리 겹침 불가, 위 여유 20mm 미만 주의, 서랍 앞 350mm 미만 불가·600mm 미만 주의, 옆 간격 0~20mm 주의, 문 열림 반경 침범 불가, 창가 커튼 200mm 주의. 바퀴 유무·높이에 따라 진단 문구가 달라진다.
- 좌표: x = 0..방 가로(왼쪽 벽에 문, 오른쪽 벽에 창), z = 0..방 세로(z=0이 뒷벽). `Item.rot` 0~3(90° 단위). 책상 기준 좌표는 `lib/desk.ts`.
- 알려진 콘솔 에러: 책상 상세 뷰 진입/복귀 시 `removeChild` 에러(drei `Html` + StrictMode). **원본 코드에서도 나는 기존 이슈**이고 화면은 정상이다.

## 9. 다음 세션 시작 절차 (체크리스트)

1. `git status`, `git log --oneline | head`로 상태 확인 → `npm run dev` 또는 `preview_start react-dev`.
2. 원본 탭(`https://store.ohou.se/goods/307306`)을 열고 두 탭 모두 1280×900으로 맞춘다.
3. 6-1 → 6-2 → 6-3 순서로 고치고, 각각 4절 방식으로 측정해 원본과 비교한다.
4. 영역 하나가 끝날 때마다 사용자에게 보여 주고 확인받는다. 확인 전에는 푸시하지 않는다.
5. 푸시 후에는 Vercel 반영을 기다려(번들 해시 변경 확인) 배포 주소에서 한 번 더 확인한다.
